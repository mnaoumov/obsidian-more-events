# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Filing an issue (for AI agents and humans)

Open issues through the [issue forms](https://github.com/mnaoumov/obsidian-more-events/issues/new/choose), not as blank issues.

Filing from the CLI or the API (`gh issue create --body`, or an AI agent filing for you) skips the form, and `gh issue create --template` cannot load an issue form. In that case, open the matching form in [`.github/ISSUE_TEMPLATE/`](https://github.com/mnaoumov/obsidian-more-events/tree/HEAD/.github/ISSUE_TEMPLATE), copy every field as a `### <label>` heading in the form's order, and fill in each one. Always state the plugin version, the Obsidian version and your operating system.

## Overview

`More Events` publishes the events Obsidian does not: named, typed, per-subject events on `app.workspace`, subscribable with no dependency beyond `obsidian` itself. It has no user interface, no settings and no commands beyond the shared **Open demo vault** one — its entire audience is other plugins.

**The first set is plugin lifecycle, and it is the FIRST rather than the whole.** Four events — one pair for a **core plugin** being enabled or disabled, one pair for a **community plugin** — each carrying that plugin's id, its display name, and `isUserInitiated`. The plugin is called `More Events` and not `Plugin Events` deliberately: a further set is published under the same contract — named, typed, per subject, plain-data payloads that only grow — and adding one is the plan rather than scope creep. What a new set still has to clear is the patch gate below; needing no patch is the ordinary case, and needing one means making that argument again from scratch. **Keep the manifest and package descriptions on that wider story too** — they are the registry listing's first impression, they are read from the RELEASED manifest, and narrowing them again costs a release to undo.

It exists because the alternative is every interested plugin monkey-patching one shared prototype. `@mnaoumov/obsidian-lib`'s own rule says a shared **global** patch belongs in a plugin rather than the library, since every consumer bundles its own copy of the library and two copies at different versions both patch. A core-plugin enable patch is exactly that shape, and `Backlink Cache` and `Backlink Full Path` each carry one today.

**So this plugin DOES patch, and that is what makes the promise true rather than breaking it.** It installs exactly the patch the rule above prescribes — one, in a plugin, once per vault — and only where a patch earns a payload member no listener could get otherwise. `isUserInitiated` is that member and, so far, the only one. The stance this replaced was *listen only, patch nothing*; it had the argument backwards, because the hazard is N patches rather than a patch, and this plugin existing is what collapses N to 1.

Prior-art gate, 2026-09-19: the 7808-entry community registry holds nothing comparable. The 17 near-matches are plugin *management* tools (Plugin Groups, Profile Manager, Device Extensions Switcher) or core-plugin *enhancers*; none publishes a signal another plugin can subscribe to.

## The seam, measured rather than assumed

Measured in `obsidian-versions/obsidian.asar/app.js` (unminified, 1.14.x public build) on 2026-09-19. **Re-measure before changing any of this; do not re-derive it from the typings, which do not carry the event at all.**

- **`InternalPlugin.prototype.enable(isEnabledByUser)` ends with `this.manager.trigger('change', this)`** (`app.js:171963`), and **`disable(isDisabledByUser)` ends with the same call** (`:171997`). `manager` is `app.internalPlugins`, declared `extends Events` by `obsidian-typings`. Both call sites are guarded — `enable` returns early when already enabled, `disable` runs only `if (this.enabled)` — so every trigger is a real transition. **Those two are also the ONLY writers of `InternalPlugin.enabled`**, which is what makes them a complete seam rather than merely a convenient one.
- **The user flag is real on BOTH sides, and the community half is the surprising one** (measured 2026-09-19). Core: the argument decides whether the instance's `onUserEnable` / `onUserDisable` runs (`app.js:171961`, `:171975`), the **Core plugins** settings toggle passes `true` (`:225422`, `:225426`), and so does the **editor-status** toggle in Editor settings (`:223751`). Community: `Plugins.enablePlugin(id, isUserEnabled = false)` forwards to `loadPlugin(id, t)`, which calls the plugin's own `onUserEnable()` when `t` (`:171247`, `:171301`, `:171063`), and `disablePlugin(id, isUserDisabled = false)` forwards to `unloadPlugin(id, t)`, which writes `plugin._userDisabled = t` (`:171328`, `:171338`, `:171078`). `enablePluginAndSave` / `disablePluginAndSave` hardcode `true` (`:171360`, `:171376`) and are what the **Community plugins** settings toggle calls (`:223543`, `:223548`).
- **`loadPlugin` / `unloadPlugin` are the only writers of `app.plugins.plugins`**, and they are called from nowhere but `enablePlugin` / `disablePlugin` (`:171301`, `:171338`; the other `loadPlugin(` hits in `app.js` are the unrelated `InternalPlugins.loadPlugin(instance)` at `:172202`). `@obsidian-typings` declares the flag on all four, and `enablePlugin` / `enablePluginAndSave` as returning `Promise<boolean>`, since `@obsidian-typings/obsidian-public-1.13.7` 1.11.0; before it the pair above carried neither the flag nor the real return type, and this repo declared a private seam interface to patch against, now deleted.
- **BUT `enablePlugin` / `disablePlugin` on the PROTOTYPE are what this plugin actually patches, and the reason is a measured trap rather than taste (2026-09-19).** `obsidian-integration-testing`'s `enablePlugin` helper saves `app.plugins.loadPlugin`, wraps it to capture load errors, enables the plugin under test — which is when this plugin's `onload` runs and installs its own patch — and then **restores the saved original in its `finally`** (`enable-plugin.mjs:9`, `:60`), silently deleting any own property installed in between. With the patch on `app.plugins.loadPlugin`, the desktop suite reported `isUserInitiated: false` for a `enablePluginAndSave` toggle; a probe showed `app.plugins.loadPlugin` back to Obsidian's own while `unloadPlugin`, patched by the same component in the same `onload`, still carried the wrapper. **Never re-point this patch at `loadPlugin` without re-reading that helper.** The harness half is tracked centrally as its own issue.
- **It is first-party and used**: Obsidian's own **Core plugins** settings tab subscribes to it (`app.js:225346`, a 100 ms-debounced redraw).
- **The community-plugin signal is much poorer.** `Plugins.didChange` is `debounce(() => trigger('changed'), 0)` (`app.js:170854`), fired from `enablePlugin`, `disablePlugin`, `uninstallPlugin`, `setEnable`, the manifest load and the update check alike (`:170938`, `:171322`, `:171341`, `:171421`, `:171524`, `:171703`, `:171815`), with **no payload at all** and a past-tense name. The diff is therefore the whole answer, and the `0` ms debounce makes it load-bearing rather than defensive.
- **`app.plugins.enabledPlugins` is NOT the set to diff, and the temptation to use it is the trap here.** It is the persisted config, and `obsidian-typings` says so in its own remark: the ids *"aren't guaranteed to be either active (in `app.plugins.plugins`) or installed (in `app.plugins.manifests`)"*. `setEnable(false)` — the master **Community plugins** switch — `disablePlugin`s every entry of `app.plugins.plugins` and **never touches `enabledPlugins`** (`:171483`), so a diff of the set announces nothing while every plugin in the vault is unloaded. `app.plugins.plugins` is the set that moves, and it is also what `getPlugin()` answers from, which is why the events mean **loaded / unloaded**.

- **The view's empty-area menu fires nothing** (`:189581`): the **Bookmarks** view's `containerEl` carries one `contextmenu` listener (`:189406`) that, unless a bookmark already called `preventDefault`, shows `new Menu()` with **New group** synchronously.
- **A canvas's empty-background menu fires nothing** (`:194500`): the canvas binds one `contextmenu` listener on its `wrapperEl` at construction (`:192611`), which shows `new Menu()` synchronously when the click's target is the wrapper itself and the canvas is not read-only. The view keeps every item in `view.doms`, by property name (`:206319`), which is how `currentTarget` is matched back to its item. The menu acts on the whole `view.tree.selectedDoms` when the item is part of a multiple selection, else on that item (`:205762`), and `more-events:all-properties-menu` names the same properties.
- **A Web viewer History item's menu fires nothing** (`:173375`): each item of the `webviewer-history` view binds one `contextmenu` listener on its `selfEl` (`:173333`), and the view keeps them in the `itemDoms` map (`:173295`). `more-events:web-viewer-history-menu` hands over a plain `{ title, url }` copy of the stored entry. The plugin's `onEnable` opens its IndexedDB store without awaiting it (`:173542`), and `addHistoryItem` silently does nothing until it is open, which the desktop suite waits out.
- **A PDF thumbnail's menu fires nothing** (`:154802`): the viewer binds one `contextmenu` listener on its sidebar container when it is built (`:154187`), and shows `new Menu()` with **Copy link to page** synchronously when the click's target is a `.thumbnail`, reading the page from its `data-page-number`. The sidebar starts closed, translated off the view's left edge with its thumbnails rendered, so the desktop suite opens it through PDF.js's `pdfSidebar.open()` first. Only PDF leaves (`getLeavesOfType('pdf')`) are searched, so a PDF embedded in a note is not announced.
- **An `await` before the show does NOT make a menu deferred by itself; what it awaits does (measured in the real app, 2026-10-26).** A trusted event runs a microtask checkpoint after each listener returns, while it is still being dispatched, so an `await` on something already settled resumes with `currentTarget` still the listener's element. Measured in catalyst 1.15.0 (`obsidian-versions/obsidian.asar`), the line numbers below are that build's.
- **A PDF outline item's menu is therefore BOTH kinds.** Each outline tree item binds one `contextmenu` listener on its `selfEl` (`:124814`), and `onItemContextMenu` (`:125014`) awaits `getMarkdownLink()`, which awaits the item's destination and page number. ## Architecture

- `api.d.ts` (repo ROOT) — the consumer-facing declarations: the event-name literal types, the payloads, `MoreEventsApi`, and the `Workspace.on` augmentations. Hand-written, self-contained, importing only from the `obsidian` package (`obsidian`, and `obsidian/canvas.d.ts` for the canvas relays' plain data).
- `api-contract.ts` (repo ROOT) — the registry contract, `MORE_EVENTS_API_CONTRACT`: an `input` and an `output` schema for every method of `MoreEventsApi`, copyable beside `api.d.ts` on the same terms. It is the constant alone: the contract type, the Standard Schema builders and the common guards come from the `api-contract` entry point of `@mnaoumov/typescript-lib` (`1.3.0` or later), the one dependency a consumer copying it takes on beyond `./api.d.ts`. `defineApiContract<MoreEventsApi>` types it, so a new API member needs both schemas or it refuses to compile. Its builders come from `createApiContractSchemaBuilders('more-events')`, which binds that vendor once for every schema, since the library's default vendor is its own name. It is not `api.ts` because TypeScript would resolve `./api.d.ts` to that file's own declarations.
- `src/api/more-events-api.ts` — the runtime half: the four event-name constants, the registry contract and its version. `PLUGIN_API_CONTRACT` is `MORE_EVENTS_API_CONTRACT` assigned to `ApiContract` from `@mnaoumov/typescript-lib/api-contract`, which is what checks its schemas are ones the registry accepts, and the plugin publishes that same constant. It **imports the types from `../../api.d.ts`** rather than re-declaring them, so there is one declaration of each.
- `src/api/more-events-api-impl.ts` — a thin delegate implementing `MoreEventsApi` over the two components below.
- `src/plugin-lifecycle/plugin-events-component-base.ts` — the snapshot-then-diff machinery both event sources share: take the baseline on load, install the subclass's patch, subscribe, and on each signal diff the last known id-to-name map against a fresh read. It also owns the id-to-`isUserInitiated` map the patches write and the diff consumes, and declares `UserInitiationRecorder` — the one method a patch component is handed, so a patch can never reach the diff, the snapshot or the events.
- `src/plugin-lifecycle/internal-plugin-patch-component.ts` — patches `enable` / `disable` on the `InternalPlugin` PROTOTYPE, reached through any entry of `app.internalPlugins.plugins` because the class is not exported.

## Invariants that are easy to break

- **A patch has to EARN a payload member or an event, and the three here are the whole of what has been allowed.** Patching is permitted, but only where it recovers context a listener cannot get any other way; it is not permission to patch for its own sake, and a fourth patch needs the same argument made again from scratch. The two plugin-lifecycle patches recover one thing, `isUserInitiated`, from the argument Obsidian itself takes and then drops. The `Menu` patch earns the context-menu events Obsidian raises none for, and it is ONE patch for all of them: a new menu of that kind is a new `MenuAnnouncer`, `DeferredMenuAnnouncer` or `PositionedMenuAnnouncer`, never a new patch. Its handler on `showAtPosition` is not a fourth patch: `showAtMouseEvent` itself shows through that method, so it is the same show path, in the same component. The capture-phase window listener that records event paths is not a patch: it replaces nothing and only reads the event.
- **A menu event fires BEFORE the original `showAtMouseEvent` or `showAtPosition`.** `showAtPosition` starts by loading the menu, and `addItem` on a loaded menu is silently ignored, so an announcement after the original would reach every listener and add nothing.
- **A relay of an Obsidian event is only as good as that event's name**, and the name is undocumented. The desktop suite is what notices a rename, so a relayed event always has one.
- **A patch must be transparent, and the unit suites assert it.** Each handler records and then returns `fallback()`, so the original's return value and its own effects — the instance's `onUserEnable` / `onUserDisable`, the plugin's `_userDisabled` — are untouched. `onUserEnable` in particular is the hook `Backlink Cache` and `Backlink Full Path` patch for themselves, so swallowing it would break the very consumers this plugin exists for.
- **Record-then-consume, and it cannot be simplified into handing the flag straight to the handler.** The core `change` fires synchronously inside `enable` / `disable`; the community `changed` is debounced and lands on a later task. So the patch can neither pass the flag across directly nor clear its own entry in a `finally` — that would wipe the community half before the signal arrived. It writes into the map and the diff deletes as it reads, which is sound only because those patched methods are the only writers of the state being diffed.
- **`isUserInitiated` is Obsidian's notion, not a wider one, and the docs must keep saying so.** It means that plugin's own toggle. The master **Community plugins** switch (`setEnable(false)`, which forwards no flag) and restricted mode are both a person's doing and both report `false`. Widening it would mean inventing a signal Obsidian does not have.
- **The event names and the payloads are a WIRE CONTRACT.** Consumers hardcode the strings; a rename breaks every plugin already listening and compiles perfectly here. `src/api/more-events-api.test.ts` asserts the literals for that reason — it is not a tautology test. `PLUGIN_API_VERSION` moves with the contract and not with the plugin: the community pair was additive, so it went to `1.1.0`, `isUserInitiated` was additive too, so it went to `1.2.0`, and the context-menu events (the bookmarks pair, the canvas view one and the ribbon one, all in one release) went to `1.3.0`, and the All properties and History item menus, the PDF thumbnail, outline item and page menus, the sidebar toggle menu, the community plugin row menu, the callout menu, the two plugin settings tab menus, the table cell and drag handle menus, the property value menu, the Bases column header menu, the property menu, the CSS snippet row menu, the external image menu, the Bases board column menu, the vault name menu, the back and forward history menus, the Bases view settings menu and the `leaf-menu` / `tab-group-menu` / `search:results-menu` / `markdown-viewport-menu` / `markdown-properties-menu` / `canvas:node-menu` / `canvas:edge-menu` / `canvas:selection-menu` / `canvas:node-connection-drop-menu` relays to `1.4.0`, and the canvas selection toolbar's **Align**, **Line direction** and group background menus to `1.5.0` — a consumer asking `^1` was undisturbed by any of them.
- **The payloads are plain data and only ever grow.** No class instances, no types owned by this repo: they cross between plugins that share no code. The two pairs carry deliberately DIFFERENT key names (`corePluginId` / `communityPluginId`) rather than a shared `pluginId` plus a kind flag, because a consumer almost always wants exactly one of the two and a flag it can forget to check is a bug waiting to happen.
- **`getPluginApis()` is the only accessor.** Never `publishPluginApi` by hand — the `plugin-loaded` broadcast's `apiVersions` is derived from `getPluginApis()` alone, so a hand call announces this plugin as publishing no API while the registry still works, which makes the mistake invisible from inside this repo. No instance `api` getter either.
- **The baseline snapshot is taken before subscribing** — in `PluginEventsComponentBase.onload`, for both halves. Reversed, the first signal would announce every already-enabled plugin as newly enabled.
- **Diff, never trust the signal's payload.** The core one passes the `InternalPlugin` that moved and the community one passes nothing at all, but a diff is correct when one signal follows several transitions and does not depend on an undocumented argument.
- **Disabled events are announced before enabled ones**, in that same base class. An update unloads a plugin and loads the new build, and both halves can land in one signal; a consumer that re-reads on the enabled event must not then be told the plugin left.
- **No `isBuiltOnObsidianLib`-style flag in the community payload, and this was decided rather than overlooked.** A fleet plugin raises both this pair and the `obsidian-lib:plugin-loaded` / `-unloaded` broadcast that `@mnaoumov/obsidian-lib` raises; detecting which plugins those are from outside is a guess, and the payload is additive-only so a flag can never be taken back. The overlap is stated in the README and in the demo vault instead.

## Deviations from the standard plugin architecture

The workspace convention is that all plugins share the same architecture; intentional deviations are documented here.

- **No settings, no settings tab, no `src/plugin-settings*.ts`.** There is nothing a user could sensibly configure about an event bus. The demo-vault coverage suite is registered without a config interface accordingly, which `@mnaoumov/obsidian-dev-toolkit` supports explicitly. `Root Folder Context Menu` and `Fix Tab Size` are the other settings-free plugins in the fleet.
- **No `src/styles/`.** The plugin renders nothing. The 0-byte-`styles.css` release trap below therefore cannot apply — there is no stylesheet at all, so no empty asset is produced.

## Screenshots, and what one can honestly show for a plugin with no UI

Four frames — `images/screenshots/screenshot-desktop-{1,2}.png` at 1200x800 and `screenshot-mobile-{1,2}.png` at 900x1600 — captured by `src/demo-vault/screenshots.desktop-capture.integration.test.ts` and `src/demo-vault/screenshots.android-capture.integration.test.ts`, and written **only** by `npm run capture:screenshots`. Their `*-capture.` infix matches none of the standard project globs on purpose, so `npm run test:integration` never rewrites the PNGs and never dirties the tree mid-release.

**The decision, 2026-09-19.** This plugin has no settings tab, no modal, no view, no ribbon icon and no command but the shared **Open demo vault** one, so there is no screen *of the plugin* to photograph. The frames are of **Settings -> Core plugins** and **Settings -> Community plugins** — the screen where the change actually happens — with a notice on it raised by a listener the suite registers. Cause and effect are then in one picture, the picture is a screen a reader can reach, and nothing in it claims a UI this plugin does not have. Three alternatives were refused: shipping no block at all, because a real reachable screen does exist; a DevTools console showing the events arrive, because `captureObsidianScreenshot` photographs the Obsidian window and DevTools is a separate one; and a screenshot of source, which is not a screenshot of the plugin and which the README already carries as copyable text.

**Not the demo vault**, though its notes do the same thing with buttons. The capture suites open the plain temporary vault the harness stages, as every other plugin of mine does; pointing this one at `demo-vault-global-setup.ts` would put `CodeScript Toolkit` in the capture path to buy background prose the Settings tab already supplies.

**Both pairs are byte-reproducible; the desktop pair took two fixes to get there.** Two emulator runs had always produced identical mobile PNGs. Three desktop runs produced three different files, differing in exactly 349 pixels at `x:153-197 y:774-783` — the temporary vault's name, whose six-character suffix is random per run, showing through the caption band, which was drawn at 94 % opacity and therefore attenuated what was under it rather than hiding it (`obsidian-integration-testing` 16.0.0 made the band opaque; the frames were re-shot on 17 on 2026-09-24). Invisible to a reader, but it meant `npm run capture:screenshots` always left a dirty tree on the desktop leg, so a diff there proved nothing on its own. **The second source, measured 2026-09-24 and fixed on 2026-09-25:** two back-to-back captures differed in 17 pixels of `screenshot-desktop-2.png` at `x:104 y:80-96`. That was the text caret blinking in the Settings modal's search box, which Obsidian focuses when the modal opens, so whichever phase of the blink the shutter caught decided the bytes. `screenshot-desktop-1.png` shows the same modal and was exposed the same way. Since `obsidian-integration-testing` 17.1.0, `captureObsidianScreenshot` hides the focused element's caret for the frame by default (`shouldHideCaret`), so nothing of this is left locally. `shoot` blurred the field for a day before that; dropping the blur on 2026-09-25 kept the focus, so both desktop frames were re-shot and now show the search box's focus ring with no caret. That is what a reader sees when the modal opens. Three captures in a row gave identical bytes on both frames. A desktop diff after a capture is now a real change. **One such change so far, and it was the harness:** `obsidian-integration-testing` 17.3.0 renders the owned instance on the CPU rather than the GPU, which moved about 140 000 pixels of each desktop frame by 1-2 levels, nearly all of them anti-aliasing. On 2026-09-28 17.1.0 still reproduced the committed bytes and 17.3.0 differed from them identically with the old and the new suite, so both frames were re-shot on 17.3.0 on purpose. The same bump moved the dark theme from a bare `app.changeTheme('obsidian')` in a closure to the harness's `applyObsidianTheme`, which saves at once. A config reload landing inside `changeTheme`'s one-second save delay would have dropped `theme` and shot every frame light. `captureObsidianScreenshot` now refuses a frame the theme has left. The Android suite keeps `changeTheme`, because no host watcher feeds `app.json` events on a device.

**The fix is a hide keyed on the vault name rather than on a class of Obsidian's chrome, and since `obsidian-integration-testing` 15.0.0 the HARNESS applies it.** `captureObsidianScreenshot` calls Obsidian's `hide()` on every leaf element whose `textContent` is `app.vault.getName()` — today that is the vault-switcher row at the bottom of the left sidedock — before every frame it takes, by default, with `shouldHideVaultName: false` to opt out and photograph the switcher itself. The varying thing is the DATA, and that row has moved between Obsidian versions before, which is why no selector is hardcoded; `hide()` rather than an inline `style.visibility` or an injected stylesheet, because `obsidianmd/no-static-styles-assignment` and `obsidianmd/no-forbidden-elements` refuse those respectively. This repo carried a local copy of that helper for a few hours on 2026-09-19 and **nothing of it is left locally**: the harness's own integration suite asserts the non-zero count, that a capture applies the hide without being asked, that `shouldHideVaultName: false` skips it, and that two differently-named vaults produce identical bytes — so the loud failure that used to live in `shoot` is one layer down, guarding every repo that captures a desktop frame instead of this one alone. The hide is a no-op on mobile, where the app renders no vault-switcher row at all and a count of zero is the right answer; the mobile pair was byte-reproducible before any of this and its bytes did not move.

**`labelScreenshot` REFUSES a caption too wide for its frame as of `obsidian-integration-testing` 15.0.0; before that it silently CLIPPED one, at both ends.** The first captured pair shipped exactly that — a sentence fragment with no hint anything was lost, in a frame of exactly the right size, so every dimension assertion downstream still passed and the only feedback was looking at the PNG. Now the caption is measured against the band's room and an overlong one throws with both numbers in the message. `measureLabelCaption({ imageHeightInPixels, imageWidthInPixels, text })` asks the same question without capturing anything, which is how to check a reworded caption. Measured that way on 2026-09-19, the four shipped captions against their own frames: desktop 1005 px and 1034 px of 1104 px available, mobile 760 px and 782 px of 828 px — 91-94 % of the room, all four fitting. Those numbers replace the earlier character-count estimate of roughly 58 and 55 characters, derived from the band's `width * 0.034` font size; em dashes and capitals are wider than any such average implies, so measure rather than count.

## The README is a landing page

**A new event adds exactly ONE row to its demo-vault note's table** (`01 Core plugin events`, `02 Community plugin events` or `04 Context menu events`, rows sorted by event name): the name, what it fires for, and its payload or the arguments after `menu`, marked *relay* when it relays an Obsidian event. Its explanation, measurements, edge cases and live buttons belong in that note too. **The README changes only when a new SET of events appears**: one short line naming the set, with one example event and a link to its note, never one row per event. The mechanism (why it patches, how menus are told apart) lives in `demo-vault/05 Why it patches.md`.

## Release traps

- **The plugin id `more-events` is permanent.** The community directory has listed it since 2026-09-30, and a listed id can never be renamed.
- **The demo-vault asset is `more-events-demo-vault.zip`, unversioned**, and it unzips into one `more-events-demo-vault-<version>` folder. Do not reintroduce the versioned asset name — no release produces it.
- **The demo-vault suite floors `CodeScript Toolkit` at `minVersion: '15.0.0'`** in `scripts/demo-vault-global-setup.ts`. `demoSetup.ts` reaches this plugin's API through the `@mnaoumov/obsidian-lib` copy that `CodeScript Toolkit` serves, and only 15.0.0 serves obsidian-lib 6, the registry this plugin publishes on. Without the floor, the harness reuses whatever gitignored copy a warm checkout already has. The `1.1.1` preflight failed that way on a 13.7.1 copy, with `Failed to load module: .../demoSetup.ts` on every button. Raise the floor when the plugin moves to a lib major that a newer `CodeScript Toolkit` is the first to serve.
- **`scripts/version.ts` carries no template-release guard, and must stay that way.** The sample-plugin-extended template disables its own release with such a guard; a scaffold that copies it re-arms it against the new plugin and makes every release throw.
